# 项目参考文档

> 电商客服 Agentic AI 系统。基于 LangGraph 做意图路由，分发到订单查询、售后决策、闲聊兜底三条链路。
> 本文档只描述**代码当前实际的样子**，不写规划中的功能。

---

## 一、整体结构

```
app/
├── main.py                     FastAPI 入口（lifespan 里建 PG checkpointer + Redis）
├── html/                       login.html / chat.html（Vue2 + SSE）
├── router/
│   ├── chat_router.py          POST /create_session、GET /chat/stream（SSE）
│   └── login_router.py
├── agent/
│   ├── graph/customer_graph.py 主图 + 会话锁 + SSE 流式
│   ├── node/
│   │   ├── intent_node.py      一级意图识别
│   │   ├── manager_node.py     中枢路由
│   │   ├── chat_node.py        闲聊兜底
│   │   ├── order_node.py       订单查询子图 wrapper
│   │   ├── after_sales_node.py 售后子图 wrapper（含支付宝真实调用）
│   │   ├── order_query/        订单查询子图（Text2SQL）
│   │   └── after_sales/        售后决策子图（规则 + LLM）
│   ├── memory/                 四层记忆
│   ├── state/                  CustomerServiceState
│   └── model/my_model.py       云端 / 本地模型单例
└── tool/
    ├── mysql_tool.py           只读查询（三层防线）
    ├── order_facts_tool.py     售后事实聚合（0 次 LLM）
    ├── policy_retrieval_tool.py 政策条款级 RAG
    └── mcp/                    支付（真实）/ 物流（桩）/ 工单（桩）
```

主图只有 5 个节点：

```
START → intent → manager ─┬→ order（订单查询子图）
                          ├→ after_sales（售后决策子图）
                          └→ chat（闲聊兜底）→ END
```

`order` / `after_sales` 执行完直接 `goto=END`；`chat` 走静态边到 `END`。

**意图识别带上下文**：`intent_node` 会把最近 6 条消息一起喂给模型。
不带的话，"我们刚刚讨论的订单是哪个"会被当成"查订单"路由到 Text2SQL，
而它其实是在问对话本身，应该走 `chat` 用记忆回答。
判断口诀是：主语是"我买的/我的订单"→ 查库；主语是"我们刚才/今天聊的"→ chat。

## 二、两条子图

### 1. 订单查询子图（Text2SQL）

```
query_rewrite → intent_classify → schema_select → sql_generate → sql_check ⇄ sql_execute → answer_translate
```

- **query_rewrite**：消解"那它到哪了"这类省略指代（无指代时不调模型）
- **schema_select**：按意图裁剪表结构（`INTENT_TO_SCHEMA` 硬编码——Neo4j 图谱暂不做）
- **sql_generate**：只生成 SQL，不执行；失败把 `db_error` 拼回提示词重试
- **sql_check**：三层防线之一——禁写关键字 / 必须 `SELECT|WITH` 开头 / 强制 `{user_id}`
- **sql_execute**：只读执行，同时回收命中的 `order_id`
- **answer_translate**：状态码翻译 + 中文答复

### 2. 售后决策子图（规则引擎 + LLM）

```
intent_slot ─┬(纯政策咨询)→ policy_rules
             ├(缺槽位)→ clarify → END
             └→ order_facts → policy_rules ─┬(冲突)→ llm_reasoning ─┬→ clarify → END
                                            │                        └→ solution_generate
                                            └(无冲突)→ solution_generate ─┬(需执行)→ action_execute → END
                                                                           └→ END
```

| 节点 | 职责 |
|---|---|
| `intent_slot_node` | 一次结构化调用同时出「13 类售后意图 + 槽位 + order_id」 |
| `order_facts_node` | 参数化查库拿固定字段集合；用库里已有售后单补全 reason 槽位 |
| `policy_rules_node` | 两跳政策检索 + 遍历 10 条规则 + 合并决策 + 判冲突 |
| `llm_reasoning_node` | 只在冲突时进入；只接受真实存在的条款编号，防编造依据 |
| `solution_generate_node` | 决策锁定 + 执行参数计算 + 生成答复 |
| `clarify_node` | 反问（单轮最多 2 次） |
| `action_execute_node` | 工单走桩；退款/收款只标记 pending，交给外层 `after_sales_node` |

**规则引擎边界**：时效、金额、品类、既有售后单由程序判定；责任归属、替代方案由 LLM 判。
规则 fail 时不直接拒绝，而是标记 `conflict_detected` 交给 LLM 复核。
`informational=True` 的规则（如"没有运费险"）只影响运费归属，**绝不构成拒绝理由**。

**两跳检索**：第一跳已命中满 `top_k` 就直接用；否则由 LLM 判断覆盖度并给出补充检索词，
按新词再检一次后合并去重。检索工具本身保持纯函数，跳不跳由 agent 层决定。

## 三、多轮上下文与记忆

两条腿：

1. **Checkpointer（PostgreSQL）**：`thread_id = session_id`，保存完整 `messages` 与
   `current_order_id`、`order_context` 等标量通道。标量字段本轮没传时自动保留上一轮值，
   这是"接着上一笔订单追问"能成立的原因。
2. **四层记忆**：

| 层 | 存储 | 作用 |
|---|---|---|
| 窗口记忆 | Redis List | 最近 N 条对话（N 由 `.env` 的 `WINDOW_MEMORY_ROUNDS` 控制） |
| 会话摘要 | PostgreSQL | 压缩历史，避免长对话爆上下文 |
| 长期偏好 | ChromaDB | 按用户存偏好，向量检索相关条目 |
| 用户画像 | Redis | 称呼、长期特征 |

记忆上下文走 **`memory_context` 独立通道**，不塞进 `messages`：
它是"背景"而不是"对话回合"，塞进去会被 Checkpointer 每轮重复持久化一份。

记忆更新（3 次 LLM 调用）放在 `asyncio.create_task` 里后台跑，
否则前端要等它跑完才收到 `done`，输入框会一直锁着。

## 四、MCP 集成

对外只经 `app/tool/mcp/__init__.py`：

| 能力 | 文件 | 状态 |
|---|---|---|
| 支付宝（退款/收款/查单） | `alipay.py` | **真实**，连阿里云百炼 MCP 广场 SSE |
| 物流查询 | `logistics.py` | 桩，返回写死的两行 |
| 售后工单 | `ticket.py` | 桩，返回写死的两行 |

支付为什么不在子图里调：MCP 是异步网络请求，子图节点是同步函数。
分工是——`action_execute_node` 只标记 `{"pending": True, "tool": "refund"}`，
真实调用集中在 `after_sales_node`（async）里的一处。

> **金额永远不由 LLM 决定**：金额在 `policy_rules_node` / `solution_generate_node`
> 用订单实付算出，执行层只负责调用。

## 五、流式输出

流式只在一处：`customer_graph.chat()` 里的
`graph.astream(..., stream_mode=["messages","custom"])`，逐条 `yield` 给 SSE。

节点只负责返回一条 `AIMessage`。**节点里不要套 `create_agent` 再 astream**：
`create_agent` 是子图，模型调用落在嵌套命名空间里，外层过滤掉，token 冒不出来
（实测：直接调模型 → 14 个 token 事件；套一层 → 只有 1 个完整消息事件）。

## 六、关键设计取舍

**为什么售后不复用订单查询子图？**
订单子图解决"不知道用户要查什么"，需要 Text2SQL 的灵活性；
售后要的是固定字段集合（签收天数、实付金额、品类、运费险、既有售后单），
用参数化查询 0 次 LLM、结果精确。拿不确定的 SQL 去驱动退款是事故。

**为什么"已有售后单"直接短路？**
这是硬业务约束而非政策灰区，让 LLM 去裁决只会引入不确定性。

**签收是时效的第一道门**
未签收 → 商品在途中，随时可退；已签收 → 才开始算 7 天无理由 / 15 天换货。

## 七、运行与自测

```bash
python app/main.py            # 启动，自动打开 http://127.0.0.1:8001/login
```

> Windows 下必须在 **Selector 事件循环**里跑：psycopg 3 不支持 ProactorEventLoop。
> `main.py` 已经设置好；自己写脚本测试时也要 `asyncio.set_event_loop_policy(...)`。

单文件自测：

```bash
python -m app.tool.policy_retrieval_tool        # 政策条款切分与检索
python -m app.tool.order_facts_tool             # 订单事实聚合（需要 MySQL）
python -m app.tool.mcp.alipay                   # 连通支付宝 MCP，建 5 元收款单
python -m app.agent.node.after_sales_node       # 售后完整链路（会真退款）
```

## 八、环境变量

| 变量 | 用途 |
|---|---|
| `DASHSCOPE_API_KEY` / `OPENAI_API_BASE` / `MODEL_LINE_NAME` | 云端模型（Qwen） |
| `LOCAL_URL` / `MODEL_LOCAL_NAME` | 本地模型（Ollama） |
| `DB_HOST` / `DB_PORT` / `DB_USER` / `DB_PASSWORD` / `DB_NAME` | MySQL 业务库 |
| `POSTGRESQL_URL` | Checkpointer + 会话摘要 |
| `REDIS_*` | 会话锁、会话表、窗口记忆、用户画像 |
| `CHROMA_PATH` | 长期记忆 |
| `EMBEDDING_MODEL_PATH` | 政策 RAG 的向量模型 |
| `WINDOW_MEMORY_ROUNDS` / `WINDOW_MEMORY_TIME` | 窗口记忆条数 / 过期秒数 |

## 九、与项目描述的差异

- **Neo4j Schema 图谱**：未实现，`schema_select_node` 用 `INTENT_TO_SCHEMA` 硬编码映射。
- **物流 / 工单 MCP**：未接真实服务，返回写死两行字符串（接口形态与真实 MCP 一致，
  将来替换只需改 `logistics.py` / `ticket.py`）。
- **政策 RAG 已实现两跳**，但第二跳的判定是"第一跳未命中满额"时才触发。
